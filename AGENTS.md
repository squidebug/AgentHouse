# Working on AgentHouse

Notes for coding agents (and people) changing this repository. Keep it short and true: update it in the same commit as the change it describes.

## What runs where

AgentHouse is three programs plus a browser app. Know which one a file runs in before changing it.

| Process | Files | Restart |
|---|---|---|
| Browser | `apps/web/src` (React + MUI) | reload |
| Web server | everything else in `apps/server/src` (`main.ts`, `web/`, ...) | freely; `tsx watch` restarts it in dev |
| Session host | `apps/server/src/host/` and what it loads: `src/shared/`, `src/claude/status.ts`, `agents.ts`, `background.ts`, `json.ts`, `sessions.ts` and `settings.ts`, `packages/protocol/src/` | ends every session: `pnpm dev:stop` (dev) or `pnpm stop` |
| Relay | `apps/server/src/relay/relay.cjs`, run by Claude Code for each hook and as its status line and sub-agent status line | per event |

- `src/claude/` is what AgentHouse knows about Claude Code (hook events, status line, settings files, sub-agents in `agents.ts`, background work in `background.ts`, the transcript format and where a transcript is in `transcript.ts`, the sessions it lists itself in `sessions.ts`, since which version it has what in `versions.ts`, and the user's notes for it: skills in `skills.ts`, CLAUDE.md and memory in `memory.ts`, read and saved through `notes.ts`); `src/shared/` is used by both servers.
- The conversation view is read in the web server (`web/conversations.ts`): only the transcripts the host reported (a sub-agent's next to its session's), only under Claude's projects folder, in small pieces so the event loop stays free. The flow view (`workspace/flow.ts`) asks for the turns only (`turns=only`). What a session was last asked and what it last said, for a glance at many sessions, comes from the end of its latest transcript alone, read when asked for and kept in memory only, until that transcript changes (`GET /api/sessions/:id/latest`, `Conversations.latest`, `latestWords` in `claude/transcript.ts`).
- The session host owns the PTYs, so sessions survive web server restarts. The web server prepares launches, checks the environment, serves the UI and relays terminals to the host.
- Browser ↔ web server types: `packages/protocol`. Web server ↔ host messages: `apps/server/src/shared/host-protocol.ts`; bump `HOST_PROTOCOL` whenever they change, and keep the hello's proof and the `shutdown` request as they are, so `--stop` still reaches older hosts. The host's token stays in its state file: on every connection the web server presents an HMAC of it over a nonce of its own (`webProof`), and the host answers with its own (`hostProof`), so whatever listens on a dead host's port is told nothing it could use. Only a host from before protocol 8 is sent the token itself.
- The web server's HTTP side (`web/http/`): `server.ts` is the door (Host, login, Origin, the page's files, and what a request that failed is told) and makes what the rest works with. The API behind it is a table in `routes.ts`: a line per route (method, path, what answers it), and a new route is a new line. A route returns the body of its answer and throws what it refuses; `refusal` gives each kind of refusal its status. A body is held to its schema in `schemas.ts`, and a schema to the type of `packages/protocol` the page sends it as. What a page keeps open is in `sockets.ts`: its events, a conversation as it grows, and a session's terminal relayed to the host.
- Until the host restarts after its code changed, the environment check warns (`shared/build.ts` hashes the files listed above).
- Claude status comes from hooks (`claude/status.ts`: `STATUS_EVENTS` and its handler map are the single list the injected hooks are built from), the status line (model, effort, context, plan limits) and, when no hook can tell (Esc, a dialog answered in the terminal), the transcript and `claude agents --json` (`claude/sessions.ts`: how that list is asked for and read, by the host and by the web server).
- Delegation (`web/delegations.ts`, web server): text sent to an idle delegated session through the composer path; done once that session is idle with no sub-agent running and idle again since the last one it started ended (that one's report is a turn of its own); its last answer after the send is read from its transcript and, when the user says so, composed into the parent (queued while the parent is busy or asking, never typed into a dialog).
- The page: the login (`LoginGate`), then the start screen (`StartupCheck`: a loading bar while `/api/env` answers; it stops on errors, and on warnings the user has not gone on past before; notes stay in the environment check), then the workspace. The start screen is for a tab's first load: a reload goes straight to the workspace.
- What is dragged and dropped in the page (`apps/web/src/workspace/state.ts`, free of React, and `dnd.ts`): a place that takes drops only names what it is (`dnd.drop(target)`). What a drop does to the layout is the reducer's; what it asks of the server (`dropEffect`: back to the top, work for a delegate) is asked in one place, by what `App.tsx` gives `makeDnd`.
- The dashboard (the switch in the top bar; `components/Dashboard.tsx`, its places and order in `workspace/dashboard.ts`): every session as a card, by what it is doing (waiting for the user, at work, living by a scheduled prompt, idle, ended), with what runs in it now listed in the card, and what it was last asked and said (`/latest`, asked for by the card). It lies over the workspace, which stays mounted under it, hidden and inert but never out of the layout: a terminal fitted to a box without a size would shrink to a few cells and resize its PTY.
- CLIs run as found on PATH (`web/cli/resolve.ts`, the first is the one the user's shell runs) unless the user chose a file (`PUT /api/cli/:vendor`, checked by its `--version`); a launch looks again when the file it would run is gone, and never falls back from a chosen file.
- An ended Claude session starts again where its conversation stopped (`SessionManager.resume` in `web/manager.ts`): `claude --resume <its id>` in its folder, with what it was launched with, under the AgentHouse id it had, so its row, links, delegations and panes stay. The host takes an id again once it has let go of it: one that saw the session end is asked to close it first. Nothing of the host changed for this.
- Sessions started outside AgentHouse, in a terminal or an editor (web server: `web/external.ts`; the host knows nothing of them): Claude Code lists every session of the user's on this machine (`claude agents --json`). The web server asks it every 10 s while a page is open and the user has not turned that off (the bell's 외부 세션 switch), leaves out the host's own (by process and conversation id) and lists the rest with the others, marked `external`. Their state comes from that list; their conversation, model and effort from the transcript named after the conversation id, under Claude's projects folder (looked for in the other projects' folders when it is not where the folder's name says). They are only read: no terminal, no messages, no links, nothing to end or remove (the server refuses these), kept in no file, gone once Claude no longer lists them. A page's first list waits for Claude's answer (2.5 s at most), so a pane restored to one of them stays. In the page they stand with the others (the tree by folder, the dashboard by what they do, the bell when they ask), each with the mark 외부 next to its name.
- Sub-agents (`claude/agents.ts`) run in the background. Hooks name them (SubagentStart/Stop; the Agent tool's result names the agent it started; events a sub-agent causes carry its `agent_id`), and the sub-agent status line adds model and tokens. Their tool calls never change the session's status; a dialog they open does.
- Background work (`claude/background.ts`, host): what a session left running (a shell command in the background, a Monitor) and the prompts set for it (CronCreate, `/loop`, a wakeup), plus the names of the skills and slash commands it ran. Built from what a tool call returned (PostToolUse), the two lists every Stop carries (they win: a task no longer listed has ended) and the prompts Claude gives the session itself (a `<task-notification>` block for a task's end or a monitor's line; a scheduled prompt is the job's own text, nothing else tells). The skills a conversation was given are read from its transcript's `skill_listing` by the web server, when asked (`GET /api/sessions/:id/skills`), followed by the project's and the user's own that lie in their folders and no listing names.
- The user's notes for Claude (web server; in the page two buttons at the foot of the session tree, a window each, `components/Library.tsx`: they are the user's and a folder's, shared by its sessions and sub-agents, so a folder is read through its latest session with a conversation, `workspace/library.ts`): a skill of the project or of the user (its `SKILL.md`), the instruction files that apply to the session (CLAUDE.md, what it imports with `@`, rules, CLAUDE.local.md) and the project's memory notes are listed, opened and saved. A request names a file of the list the server made (`/skills/:name`, `/memory/:id`), never a path. A note is a `.md` file of its folder (`noteInside` in `claude/notes.ts`: not a link out of it, not whatever else lies there); a save goes over the version the page loaded, and is refused when the file has changed on disk, since Claude writes these files too.
- What the page announces (a browser notification while its tab is hidden; the bell in the top bar, `components/Notifications.tsx`, counts and lists who waits): a session that asks and, once the user turned it on there, one whose work ended. The host sends one session list per burst of events (150 ms), so a state held for a moment may never arrive: an end is told from the list before (`workspace/notify.ts`: in a turn, then idle with no sub-agent at work), list by list as they arrive, not from what is drawn.

## State

- `~/.agenthouse/` (dev: `~/.agenthouse-dev/`; must be the user's alone, `web/state-dir.ts` checks it at start): `host-<protocol>.json` (host port and token, user-only), `web.json` (the web server serving this folder and the key local tools present to it, user-only: a second start asks it for a login address and opens that instead of running another, `--stop` ends it before the host; the dev runner keeps none), `logs/host.log` and `logs/web.log` (the web server: what it could not save, errors nothing caught, and the cause of a request that failed in the server itself: the reply to it says only that it failed), `run/<protocol>/` (per-session settings and relay config, removed when the session ends; a starting host clears leftovers).
- Written by the web server: `settings.json` (the executable the user chose per CLI in the environment check, which the doctor reads; and that sessions started outside AgentHouse are not watched, once the user turned that off), `sessions.json` (session registry: what the host reported last, so ended sessions and their transcripts stay listed after a host restart), `usage/limits-YYYY-MM.jsonl` (plan usage, a line per change; the last one shows until a session reports again), `state.json` (which session the user placed under which, grouped or delegated; one level, links of removed sessions dropped), `delegations.json` (work handed to a delegated session: where its answer is in that session's transcript, never the answer itself).
- Browser localStorage: login token (`ah-token`, per port), layout (`ah-layout`), last folder (`ah-last-cwd`), theme (`mui-mode`), the start screen's warnings the user went on past (`ah-passed-issues`), finished work announced too (`ah-notify-done`), the dashboard shown last (`ah-screen`). sessionStorage: this tab has been through the start screen (`ah-started`).
- Everything else lives in memory. There is no database: anything that must persist goes into local JSON/JSONL files under the state folder, one writer per file, written atomically (`writeJsonFile` in `shared/state.ts`).

## Commands

- `pnpm dev` / `pnpm dev:stop`: dev servers with their own state folder and port (7358); never touch the user's real sessions.
- `pnpm build`, `pnpm start` / `pnpm stop`, `pnpm run doctor [-- --json]` (the environment check in the terminal, starting nothing; exit 1 when AgentHouse cannot run; `web/doctor-command.ts`; `pnpm doctor` is pnpm's own command).
- `pnpm typecheck`, `pnpm test` (a fake agent stands in for the CLIs, no login; launched like Claude Code it sends hook events and, under a temporary `CLAUDE_CONFIG_DIR`, writes a transcript, which `--resume` goes on with; `agents` in a prompt runs background sub-agents, `approval` waits for an approval until a key is pressed, `background`, `monitor`, `schedule` and `skill` do what a Claude session's background command, Monitor, `/loop` and Skill call do; run as `agents --json` it prints what a check wrote to `agents.json` in the config folder, in place of Claude's list of sessions), `pnpm licenses:check`.
- `pnpm canary:claude [-- --turn | --resume | --scenario | --background | --external]`: the built app against the installed Claude Code; no prompt unless `--turn` (one), `--background` (haiku, low effort: a command in the background until its end is reported, a prompt set with `/loop 1m` until it has run once and is deleted, the skills of the conversation), `--resume` (one, then the session is ended and resumed and asked for what the first got; in the canary's folder) or `--scenario` (haiku, low effort: reply, approve, deny with Esc, interrupt, sub-agents (two parallel, one nested), `/clear`, work delegated to a second session and handed back, then delegated work that runs through a sub-agent, then the conversation views from the real transcripts; runs in `%TEMP%/agenthouse-canary-work` and tells Claude to trust it the first time). `--external` sends none either: a second Claude Code started directly in a terminal of its own must show as a session started outside AgentHouse, AgentHouse's own not a second time, and be gone once it ends.
- `pnpm ui:check [-- --out <folder> [--before <folder>]]`: the built app in the installed Chrome (playwright-core, nothing downloaded) with the fake agent (sub-agents included), a made-up ended session and made-up sessions started outside AgentHouse (`scripts/ui-sample.mjs`); light and dark screenshots, and with `--out` one page of them all (`index.html`, the pictures inside it, `scripts/ui-page.mjs`): light next to dark, and before next to after when `--before` names the `--out` folder of an earlier run.
- Tests that need a host use a temporary state folder (`tempStateDir()`, or `AGENTHOUSE_HOME` for a spawned server); never the real `~/.agenthouse`.

## Rules

- Users keep their setup: never require reinstalling or upgrading Node (18+) or the CLIs, or changing PATH. Detect what is there, use the install the user's shell runs, and gate features by CLI version.
- Never read credential files (`~/.claude/.credentials.json`, `~/.codex/auth.json`); never proxy model traffic.
- Change a CLI's behaviour only per session (Claude: `--settings`); never edit the user's settings files.
- Skills, CLAUDE.md and memory notes are the user's: read when the user opens one and written only by the user's own save in the page, never by AgentHouse on its own account.
- A Claude session's `--settings` deny its file tools the state folder (`stateFolderRules` in `web/cli/launch.ts`): the tokens there start programs and type into every session. They add to the user's permission rules.
- A session started outside AgentHouse is the user's, running somewhere else: it is read (Claude's list, its transcript) and nothing more. Its list comes from the documented command alone; Claude's own session files (`~/.claude/sessions/`, next to keys) are never opened. A check never asks the real CLI for it, which would list what the developer has open: with `--allow-fake` the fake agent answers, and tests give their own list (`claudeSessions`) or none.
- The relay prints nothing as a hook, always exits 0, stays fast and has no dependencies.
- Never type into a dialog: the host takes text only from a CLI that has started (Claude's folder trust question comes before any hook) and shows no dialog; dialogs are tracked apart from the status (`Dialogs` in `claude/status.ts`), and automatic sends (delegation) wait while someone types in that terminal, then ask `claude agents --json` first. Text is pasted without control characters, one at a time per session; a held-back Enter is sent again alone, never with the text.
- node-pty only on the host's main thread.
- Start programs by absolute path, or after a PATH search that skips empty and relative entries: Windows runs a same-named program from the current folder first.
- Security problems that plain CLI use also has are environment facts, not AgentHouse bugs; AgentHouse must just not make them worse.
- UI text lives in `apps/web/src/strings.ts`: short Korean labels, no explanatory or self-referential sentences. Show status, title and model by default; everything else behind the expand toggle. A card of the dashboard is the exception: it is where every session is looked at without opening any, so it also says how long the session has been as it is, what it was last asked and answered, what runs in it, and its folder, effort and context.
- Looks come from `apps/web/src/theme/tokens.ts`. Height is a tone and a shadow: the page (`bg`; the bar and the tree lie on it), a card (`surface`, `shadow1`: a pane, the row of what a pane shows), a card in use (`shadow2`: the active pane, the open composer), what floats (`raised`, `shadow3`: menus, popovers, dialogs); what is set into a card (a terminal, a conversation) has an inset edge (`well`). What a row of the tree opens is a tray on the page (`bg2`, a line around it), and what can be done there are keys that stand out of it (`thumb`, `shadow1`). Under the pointer: the `hover` veil on what has no fill, the stronger fill on a chip, a step up for a filled button. What is shown or chosen is told by its face and height, not by a tint: color is kept for status. Changes are timed by `motion`, which stands still when the system asks for less of it. Type is 12, 13, 14 or 18, in 400, 500 or 600.
- Light and dark differ only under `apps/web/src/theme/`: in the values `tokens.ts` builds (light shows a height as a shadow, dark as a lighter tone and an edge), in MUI's palette made of them and in the terminal's colors. No component has a style for one mode alone. It gives a height both its face and its shadow (`surface` with `shadow1`), so each mode shows it in its own way; to change how deep something looks in one mode, change the values.
- A change of looks never changes the size of a pane or its terminal, which would resize the PTY: height is a shadow, not a border. `pnpm ui:check` prints the pane's box and the terminal's size to compare. For the same reason a pane with a terminal is never hidden with `display: none`: what covers the workspace lies over it.
- Dependencies must pass `pnpm licenses:check`; never copy code from AGPL projects.
- No real transcripts, company data or personal paths in the repository.
- Commits: one logical change each; no `Co-Authored-By` trailers.

## Local notes (not in the repository)

If `docs/` exists, read it first: `docs/plan.md` (plan; §0 is progress, scope and next steps), `docs/facts.md` (verified facts, the source of truth), `docs/review-*.md`. After changing anything in `docs/`, run `node docs-backup/snapshot.mjs "<one-line summary>"`; it keeps every version as a new file.
